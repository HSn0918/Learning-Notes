### 一个 Go map 序列化问题，如何让你的 LLM 缓存失效

如果你在用 Go 语言开发 LLM 应用，这篇文章可能会帮你省下一大笔钱。
我们都知道，LLM 推理时可以用 KV Cache 加速。其中一个极其有效的用法，就是缓存整个 Prefill 阶段的结果。如果进来一个完全一样的 Prompt，推理引擎就能直接命中缓存，跳过最耗时的 Prefill 计算。
这个机制的关键是：**如何判断两个 Prompt “完全一样”？**
答案很简单：**直接逐字比对完整的 Prompt 字符串**。只有当两个字符串从头到尾一模一样时，系统才会认为它们是同一个 Prompt。
问题就出在这里。
#### Go map 的“随机性”陷阱

在 Go 里，遍历一个 map 的顺序是随机的。这是 Go 语言的特性，防止你依赖不确定的遍历顺序。
当你把一个 map 序列化成 JSON 字符串，用来拼接到 Prompt 中时，会发生什么？
- Go 的标准库 `encoding/json` 很“聪明”，它会**自动按 key 排序**，所以每次输出的字符串都一样。这是安全的。
- 但为了追求极致性能，你可能用了一些第三方的 JSON 库。其中有些库为了快，**并不会对 key 进行排序**，而是直接按 map 随机的内部顺序输出。
我们来看一个例子。假设你的程序有这样一个 map：

```
userInfo := map[string]string{
    "user_id": "u-123",
    "level":   "VIP",
}
```

使用一个不排序的库，两次连续的请求可能生成了两个外表不同、但内容一样的 JSON：

请求 A 的 Prompt 可能包含：

"context": {"user_id":"u-123", "level":"VIP"}

请求 B 的 Prompt 可能包含：

"context": {"level":"VIP", "user_id":"u-123"}

从逻辑上看，这俩 JSON 完全等价。

但对于需要精确匹配的推理引擎来说，这**是两个完全不同的字符串**。系统进行逐字比对时，会立刻发现差异。

结果就是 **缓存未命中（Cache Miss）**。

服务商提供的前缀缓存，其全部价值都建立在一个精确且不变的 Token 序列之上。

当你的 JSON 字符串仅仅因为键的顺序变化，从 `{"a": 1, "b": 2}` 变为 `{"b": 2, "a": 1}` 时，分词器（Tokenizer）会生成一个全新的 Token 序列。这个新序列与服务商缓存中存储的任何记录都无法匹配。

于是，前缀缓存被宣告无效。服务商的系统无法利用这份本可复用的“历史记忆”，不得不退回到最原始、最昂贵的方式——对你的整个 Prompt 重新进行一次完整的预填充（Prefill），为它从头计算一份全新的初始 KV 状态。

这就是为什么，一个由第三方 SDK 序列化方法导致的微小差异，会在我们的账单上掀起一场价值不菲的风暴。我们追求输入的确定性，本质上是在守护 LLM 服务高效推理的根基。

### **大模型推理全流程：从核心机制到服务层优化**

---

### **第一部分：核心推理机制 (单次请求内)**

这是模型处理任何一次请求都必须遵循的内部工作流程。

#### **1. 预填充 (Prefill) — 计算初始状态**

当模型接收到您的提示 (Prompt) 时，它会进入预填充阶段。

- **并行处理**：此阶段会并行处理输入的所有 Token。
    
- **生成 KV 缓存**：为每一个输入 Token 计算并生成一组关键的内部状态，称为 **KV 缓存 (Key-Value Cache)**。
    
- **记忆快照**：这些 KV 缓存可以被视为整个输入 Prompt 在模型内部的“记忆快照”或“初始状态”。
    

这是一个**计算密集型**的步骤，因为它需要一次性处理整个输入序列。

#### **2. 解码 (Decoding) — 增量生成与状态更新**

预填充完成后，模型便进入逐字 (Token by Token) 生成的解码阶段。此时，模型依赖前一阶段生成的 KV 缓存进行工作。

在生成**每一个新 Token** 时，模型会执行以下两个核心操作：

- **利用现有状态**：
    
    1. 首先，为即将生成的新 Token 计算其 **Query 向量**。
        
    2. 接着，让这个 Query 向量与内存中**所有**历史 Token 的 Key-Value 向量进行注意力计算。
        
    3. 基于注意力计算的结果，预测出下一个最可能的 Token。
        
- **更新状态**：
    
    1. 仅为这个**刚刚生成的新 Token** 计算出其自身的 KV 向量。
        
    2. 将这组新的 KV 向量追加到内存中 KV 缓存列表的末尾，供下一次生成使用。

### **第二部分：服务层优化 (跨请求间)**

在理解了单次请求的内部机制后，我们来看一个更上层的优化技术。这层优化是 LLM 服务商为了显著降低成本和延迟，在模型自身机制之上额外实现的功能。

#### **跨请求的前缀缓存 (Prefix Cache)**

它的逻辑非常直接，是核心机制的自然延伸：

> 既然为 Prompt 计算初始 “KV 状态” 的**预填充 (Prefill) 步骤非常昂贵**，那么如果很多请求的开头部分都完全一样 (例如，共享相同的系统提示或指令)，我们能不能只计算一次，然后把这份初始状态存起来，供后续所有匹配的请求重复使用呢？

答案是肯定的。这就是**前缀缓存**的工作原理：

1. **前缀匹配 (Prefix Matching)**：当服务商收到一个新请求时，它会先将 Prompt 的 Token 序列与已缓存的 “KV 状态” 记录进行前缀匹配。
    
2. **缓存命中 (Cache Hit)**：如果发现一个请求的 Token 序列前缀，与缓存中某条记录完全对应，服务商就会直接将这份预先计算好的 “KV 状态” 加载到内存中。
    
3. **跳过预填充 (Skip Prefill)**：模型因此**直接跳过了对这部分共享前缀的昂贵预填充计算**，只需对 Prompt 中超出前缀的剩余部分进行增量处理，然后立刻开始解码。
    

通过这种方式，前缀缓存极大地提高了处理相似请求的效率，尤其是在大量用户使用相似模板或系统提示的场景下。

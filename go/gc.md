#gc

相关笔记：[[gmp-model]] | [[context]] | [[map-internals]]

## 概述

Go 语言采用 **并发三色标记清除（Concurrent Tri-color Mark and Sweep）** 算法进行垃圾回收。GC 与用户代码（赋值器 mutator）并发执行，通过写屏障（write barrier）保证标记正确性，尽量减少 STW（Stop The World）停顿时间。

---

## 三色标记法原理

三色标记法将堆上所有对象分为三种颜色：

| 颜色 | 含义 | 状态 |
|------|------|------|
| **白色** | 未被访问 | 可能是垃圾，回收结束后仍为白色的对象将被回收 |
| **灰色** | 已被访问，但引用未全部扫描 | 标记波面（wavefront），待继续扫描 |
| **黑色** | 已被访问，所有引用已扫描 | 确定存活，不会指向白色对象 |

![[对象以及波面之间的关系.png]]

### 标记流程

```mermaid
flowchart LR
    S1["1. 所有对象标记为白色"] --> S2["2. 从根对象出发\n将直接引用标记为灰色"]
    S2 --> S3["3. 取出灰色对象\n扫描其引用"]
    S3 --> S4["4. 被引用对象标记为灰色\n当前对象标记为黑色"]
    S4 --> S5{灰色队列为空?}
    S5 -- No --> S3
    S5 -- Yes --> S6["5. 回收所有白色对象"]
```

具体步骤：

1. 起初所有对象都是**白色**
2. 从**根对象**（root set）出发，将所有可达对象标记为**灰色**，放入待处理队列
3. 从队列中取出灰色对象，将其引用的对象标记为灰色，自身标记为**黑色**
4. 重复步骤 3，直到队列为空
5. 剩余的白色对象即为不可达的垃圾，回收之

![[three_color.gif]]

> **根对象（Root Set）** 是 GC 标记的起点，包括：
> 1. **全局变量**：编译期确定，贯穿程序整个生命周期
> 2. **执行栈**：每个 goroutine 的栈上变量及指向堆的指针
> 3. **寄存器**：CPU 寄存器中可能指向堆内存的指针值

---

## STW（Stop The World）

STW 指从暂停所有 goroutine 到恢复执行的时间窗口。在此期间"万物静止"，赋值器不会修改对象图。

GC 过程中有两次短暂的 STW：
- **标记开始前**：开启写屏障，准备并发标记
- **标记结束后**：确认标记完成，关闭写屏障

Go 的设计目标是将 STW 时间控制在**亚毫秒级别**。

---

## 并发标记的难点 — 对象丢失问题

在并发标记过程中，赋值器可能同时修改对象引用关系，导致**存活对象被错误回收**。

### 问题场景

| 时序 | 回收器 | 赋值器 | 说明 |
|------|--------|--------|------|
| 1 | shade(A, gray) | | 根对象的子节点 A 标记为灰色 |
| 2 | shade(C, black) | | C 的子节点都已扫描，C 标记为黑色 |
| 3 | | C.ref3 = C.ref2.ref1 | 赋值器将黑色对象 C 指向白色对象 B |
| 4 | | A.ref1 = nil | 赋值器移除灰色对象 A 对白色对象 B 的引用 |
| 5 | shade(A.ref1, gray) | | A.ref1 已为 nil，无事发生 |
| 6 | shade(A, black) | | A 标记为黑色，B 永远不会被扫描到 |

```mermaid
graph LR
    subgraph "初始状态"
        C1[C 黑色] -->|ref2| A1[A 灰色]
        A1 -->|ref1| B1[B 白色]
    end

    subgraph "赋值器修改后"
        C2[C 黑色] -->|ref3| B2[B 白色]
        A2[A 灰色] -.->|ref1=nil| X[ ]
    end

    subgraph "最终结果"
        C3[C 黑色] -->|ref3| B3["B 白色 ❌ 被错误回收"]
        A3[A 黑色]
    end
```

![[gc状态.png]]

**根本原因**：黑色对象新增了对白色对象的引用，同时白色对象失去了所有来自灰色对象的引用。回收器不会重新扫描黑色对象，导致白色对象 B 被遗漏。

### 解决方案 — 写屏障

为保证并发标记正确性，Go 使用**混合写屏障（Hybrid Write Barrier）**（Go 1.8+）：

- **插入屏障**（Dijkstra）：当黑色对象新增对白色对象的引用时，将白色对象标记为灰色
- **删除屏障**（Yuasa）：当灰色/白色对象的引用被删除时，将被引用对象标记为灰色

混合写屏障结合两者优势，消除了标记终止阶段对栈的重新扫描需求。

## Go GC 完整流程

当前版本（Go 1.21+）的 GC 以 STW 为界限分为五个阶段：

| 阶段 | 说明 | 赋值器状态 |
|------|------|-----------|
| **Sweep Termination** | 清扫终止，为并发标记做准备，启动写屏障 | STW |
| **Mark** | 并发扫描标记阶段，与赋值器并发执行 | 并发 |
| **Mark Termination** | 标记终止，确保标记完成，停止写屏障 | STW |
| **GC Off (Sweep)** | 内存清扫阶段，将垃圾内存归还到堆 | 并发 |
| **GC Off (Scavenge)** | 内存归还阶段，将多余内存归还给操作系统 | 并发 |

## GC 触发条件

Go GC 有三种触发方式：

1. **堆内存达到阈值**：默认当堆大小增长到上次 GC 后的 2 倍时触发（由 `GOGC` 环境变量控制，默认 100，即 100% 增长率）
2. **定时触发**：超过 2 分钟没有触发 GC，由 `sysmon` 监控线程强制触发
3. **手动触发**：调用 `runtime.GC()` 手动触发

```go
// 调整 GC 频率
// GOGC=200 表示堆增长到 200% 时触发（更低频率）
// GOGC=off 关闭 GC
import "runtime/debug"
debug.SetGCPercent(200)

// Go 1.19+ 可设置内存软上限
debug.SetMemoryLimit(1 << 30) // 1GB
```

## 面试要点

### 高频问题

**Q: Go 的 GC 用的是什么算法？**

> [!question]- 参考答案（点击展开）
>
> Go 采用 **并发三色标记清除（Concurrent Tri-color Mark and Sweep）** 算法，无分代、无内存整理（non-generational, non-compacting）。GC 与用户代码（mutator 赋值器）并发执行，通过写屏障保证标记正确性，目标是把 STW 停顿控制在亚毫秒级别。

**Q: 三色标记法中白、灰、黑三种颜色分别代表什么？**

> [!question]- 参考答案（点击展开）
>
> **白色** 表示未被访问、可能是垃圾，回收结束后仍为白色的对象会被清除；**灰色** 表示对象本身已被访问但其引用还没扫描完，是标记波面（wavefront）；**黑色** 表示对象及其所有引用都已扫描完毕，确定存活。标记从根对象（全局变量、各 goroutine 执行栈、寄存器中的指针）出发，反复取灰色对象扫描，直到灰色队列为空，剩余白色对象即为垃圾。

**Q: 并发标记为什么会发生对象丢失？要同时满足哪两个条件？**

> [!question]- 参考答案（点击展开）
>
> 因为标记和赋值器并发，赋值器可能在标记途中改动引用关系。对象丢失需 **同时** 满足两个条件：① 一个 **黑色对象新增了对白色对象的引用**；② 该 **白色对象同时失去了所有来自灰色对象的引用**。由于回收器不会重新扫描已是黑色的对象，这个白色对象就会被遗漏并错误回收。

**Q: 什么是写屏障？Dijkstra 屏障和 Yuasa 屏障有什么区别？**

> [!question]- 参考答案（点击展开）
>
> 写屏障（write barrier）是在指针写操作时插入的一段额外逻辑，用于在并发标记期间维护三色不变性。**Dijkstra 插入屏障** 在黑色对象新增对白色对象引用时把被引用的白色对象置灰（保证强三色不变性）；**Yuasa 删除屏障** 在引用被删除时把原被引用对象置灰（保证弱三色不变性，即快照 snapshot-at-the-beginning）。两者分别破坏对象丢失的两个必要条件之一。

**Q: Go 1.8 引入的混合写屏障（Hybrid Write Barrier）解决了什么问题？**

> [!question]- 参考答案（点击展开）
>
> 在 Go 1.8 之前只用 Dijkstra 插入屏障，且出于性能考虑不对栈写操作开启屏障，导致 Mark Termination 阶段需要 STW 重新扫描所有 goroutine 栈，这个 re-scan 在 goroutine 多、栈大时可能造成较长停顿。混合写屏障结合插入屏障与删除屏障：标记开始时把当前所有栈一次性扫黑（之后无需重扫），标记期间新分配对象直接置黑，从而 **消除了标记终止阶段对栈的重新扫描**，把 STW 压到亚毫秒级。

**Q: Go GC 的完整流程分哪几个阶段？哪些阶段会 STW？**

> [!question]- 参考答案（点击展开）
>
> 当前版本以 STW 为界分五个阶段：**Sweep Termination（STW，清扫终止并开启写屏障）** → **Mark（并发标记，写屏障开启）** → **Mark Termination（STW，确认标记完成并关闭写屏障）** → **Sweep（并发清扫，把可回收内存归还到堆的空闲列表）** → **Scavenge（并发将长期空闲内存归还操作系统）**。其中只有 Sweep Termination 和 Mark Termination 两个阶段是 STW，且都很短暂。

**Q: Go GC 在什么条件下触发？GOGC 是什么含义？**

> [!question]- 参考答案（点击展开）
>
> 三种触发方式：① **堆内存阈值**，默认堆增长到上次 GC 后存活量的 2 倍时触发，由 `GOGC` 控制（默认 100，即 100% 增长率，`GOGC=off` 关闭 GC）；② **定时触发**，超过 2 分钟（`forcegcperiod`）未发生 GC 时由 `sysmon` 监控线程强制触发；③ **手动触发**，调用 `runtime.GC()`。运行期可用 `debug.SetGCPercent()` 调整频率。

**Q: GOGC 和 SetMemoryLimit 有什么区别，怎么配合使用？**

> [!question]- 参考答案（点击展开）
>
> `GOGC` 控制 GC 的相对频率（堆增长百分比），但在内存压力大、活跃堆增长快时单靠它可能 OOM。Go 1.19+ 引入 `debug.SetMemoryLimit()`（或环境变量 `GOMEMLIMIT`）设置内存软上限（soft limit），当接近上限时 GC 会更频繁运行以避免超限。常见实践是把 `GOGC` 调高甚至设为 off，再用 `GOMEMLIMIT` 兜底：既减少日常 GC 开销，又防止内存溢出。

### 面试加分点

- 能说清 **强/弱三色不变性**：强不变性要求黑色对象不指向白色对象（Dijkstra 插入屏障保证）；弱不变性允许黑指白，但要求该白色对象存在一条从灰色对象出发的可达路径（Yuasa 快照保证）。写屏障的本质就是维护其中一种不变性。
- 理解 Go GC 是 **非分代、非整理（non-moving）** 的：不像 JVM 那样有 Young/Old 分代和压缩整理，因此不会移动对象（指针稳定，利于 cgo），代价是存在内存碎片，靠 size class 的 mcache/mcentral/mspan 分配器和后台 Scavenge 缓解。
- 知道 **辅助标记（Mutator Assist / GC Assist）** 机制：当某个 goroutine 分配内存过快、可能让 GC 跟不上时，runtime 会让它"还债"，强制参与一部分标记工作，从而保证 GC 在堆翻倍前完成，避免堆失控增长。
- 了解 **Pacer（GC 步调控制器）** 的作用：它根据上一轮的标记速率和分配速率动态决定何时启动并发标记，使标记恰好在堆达到目标大小时完成；Go 1.18 对 Pacer 算法做过重写以提升稳定性。
- 能结合调优实践：高吞吐服务可调高 `GOGC` 用内存换更少的 GC 次数，延迟敏感服务则关注 STW 与 assist 开销；可通过 `GODEBUG=gctrace=1`、`runtime.ReadMemStats` 或 pprof 的 heap profile 观测 GC 行为与停顿。
- 清楚 STW 虽短但仍存在，原因是 Mark Termination 需要在一个全局静止的快照上确认标记完成并关闭写屏障；理解混合写屏障去掉栈重扫正是把 STW 从毫秒级降到亚毫秒级的关键。
